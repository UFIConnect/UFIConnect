# Security review — September 15, 2026

## Scope and release status

This review covers the local UFIConnect source snapshot at `fea83b3739a5b0e3a94f53000679cc39ca9f131f` and the changes made after it. It addresses verified authentication, credential storage, password-field, profile privacy, and administrative access problems. These are source changes; they do not establish that production has been upgraded or that historical data was never exposed.

## Verified findings and changes

| Area | Finding | Remediation |
| --- | --- | --- |
| Password reset | A reset JWT could authenticate normal API calls; links could be reused and logged | Distinct token purpose, single-use reset state, session invalidation, fragment-based links, no reset-link logging |
| Sessions | Long-lived sessions persisted in browser storage and native AsyncStorage | Memory-only web/Office tokens; OS secure storage on native; server-side session revocation |
| Passwords | Six-character creation policy; accidental copy/cut/drag; unchanged passwords could be accepted as an update | At least 15 characters for new passwords; reject bcrypt input over 72 UTF-8 bytes; local common-password screening; compare changes/resets against the authoritative current hash; explicit Show/Hide with automatic concealment and copy protection |
| Public profiles | Private role settings could be returned to another member | Explicit public-field selection and privacy controls |
| Provider sign-in | A cached Auth0 identity could remain authenticated after its local account was deleted | Authoritative database refresh and identity checks; reject missing/relinked identities and fail closed during outages |
| Connected accounts | Tokens persisted without application-level encryption despite encryption claims | AES-256-GCM authenticated encryption with a separate deployment key and legacy-data migration |
| Streams | Member and Office tokens appeared in stream URL query strings | Fetch streaming with authorization headers; server rejects query-token authentication |
| Logs and telemetry | Reset links and URL secrets could reach logging/analytics; simulated security scans claimed success | Redaction, no-referrer policy, factual control status; optional GA subsequently added with consent, fixed categories and an isolated API-origin document |
| Database | Production connections disabled certificate verification | Verify TLS certificates by default; explicit documented internal-network exception |
| Android signing | Release signing passwords were hardcoded in source | Environment-supplied signing credentials; missing release credentials fail the build |
| Dependencies | Web/Office Vite 5 and the old Expo 48 toolchain had known advisories; installs were unpinned | Vite 7.3.6, Expo SDK 57 / React Native 0.86.3, committed lockfiles, automated dependency checks; native validation is recorded in mobile/DEPENDENCY_SECURITY.md |
| Native attachments | File-detail messages included local device/browser file URIs without uploading a file | Explicit metadata allowlist removes device paths; the interface identifies these as file details only |

## User-visible behavior

- Passwords are hidden by default. Show/Hide reveals only the text entered in that field, including password-manager autofill; the server never retrieves or returns an account's password. Leaving the field, leaving the app/tab, clearing the value or submitting conceals it again. Web/Office lifecycle handlers conceal synchronously before the browser can freeze a page. Copy, cut, and drag protections remain active while revealed. Native inputs remain in secure-entry mode and show a separate non-selectable preview. Paste and password-manager autofill remain available. Native fields provide an explicit paste action where hiding the selection menu also hides the OS paste command.
- Changing or resetting to the current password is rejected without claiming success or consuming a valid reset link. A rejected change leaves the existing credential and sessions intact. A successful change atomically updates the stored hash, invalidates earlier sessions/reset links, and requires sign-in with the new password. Concurrent updates cannot both succeed against the same old credential.
- New passwords are checked against an attributed local common-password list and predictable whole-value guesses. No user password or fingerprint leaves the server for screening. See [blocklist provenance and maintenance](../backend/security-data/README.md). Case, spaces and Unicode remain supported; no arbitrary uppercase/digit/symbol mixture or periodic password expiration was added.
- Existing passwords still work at sign-in. The stronger policy applies when registering, changing, or resetting a password.
- Reloading or closing a web/Office page ends its in-memory session. Auth0 may restore a session through the provider. Native sign-in persists using secure device storage.
- Security settings provide password changes and session revocation. Provider-managed passwords and MFA remain controlled by that provider; no local MFA or passkey support is claimed.
- Clipboard protections reduce accidental disclosure. They cannot make plaintext copied into another application unreadable, protect against a malicious browser extension, or secure a compromised device.

## Required production rollout

1. **Provision `OAUTH_TOKEN_ENCRYPTION_KEY`** as a cryptographically random 32-byte value encoded in base64. Keep the same value in API and pipeline secret stores. Keep it separate from `JWT_SECRET`. Do not generate a different key on each restart; retain a securely backed-up copy for recovery. The production application fails closed without a valid key.
2. **Check `JWT_SECRET`, Office access tokens, and database credentials.** Use strong independent secrets. Rotate credentials previously exposed in URLs/logs or source; clear or tightly restrict historical log access. Rotating a signing secret requires all workers to receive the same new value.
3. **Assess Android signing exposure.** Replace the hardcoded passwords. If an upload/signing key was also exposed, follow the app-store key rotation process; a password change alone does not revoke a copied key. Provide `UFI_ANDROID_KEYSTORE_PATH`, `UFI_ANDROID_KEYSTORE_PASSWORD`, `UFI_ANDROID_KEY_ALIAS`, and `UFI_ANDROID_KEY_PASSWORD` to release builds through secret storage.
4. **Back up and migrate the database.** Deploy schema and token-encryption migrations before new clients rely on revocation. Verify migrations and encrypted credential round-trips in staging. Check backups and old file-based user stores for historical plaintext tokens. Do not erase backups until the recovery and retention requirements are understood.
5. **Verify database TLS.** Production defaults to `DATABASE_SSL_MODE=verify-full`; provide `DATABASE_SSL_CA` when a private CA is required. Render's internal URL uses self-signed TLS without certificate verification, so the blueprint requires the full external `DATABASE_URL` in API and pipeline secret settings. Restrict external database access to the services' egress IP ranges and verify connectivity in staging. The optional backup database must meet the same TLS requirements. Only an explicitly approved private/internal database connection may use `DATABASE_SSL_MODE=disable` together with `DATABASE_ALLOW_PLAINTEXT_INTERNAL=true`. Public database connections must use certificate verification. See [Render's connection guidance](https://render.com/docs/postgresql-creating-connecting#ssl-modes-for-internal-connections).
6. **Apply browser headers at the actual host.** `render.yaml` defines CSP, HSTS, no-referrer, and other headers. The web production build also includes a CSP meta policy for static hosts. GitHub Pages does not apply Render configuration, and a meta policy cannot enforce frame ancestors or HSTS. Verify the live response headers on every production hostname and install surface. Broad HTTPS media/connect sources remain for the aggregated feed; they are not an outbound data-loss-prevention boundary. Run `node scripts/sync-security-headers.mjs` after changing inline HTML scripts and verify the built hashes in CI. The explicit `X-XSS-Protection: 0` disables obsolete browser filtering in favor of CSP, including `script-src-attr 'none'`. This follows [OWASP's current guidance](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html#x-xss-protection); an older scanner may flag it, but enabling the deprecated filter can introduce vulnerabilities.
7. **Deploy backend, web, Office, and rebuilt native apps together.** Legacy JWTs are intentionally rejected. Confirm sign-in, password change/reset, logout, logout-all, Auth0, social connections, feed streams, private messaging, and mobile upgrades against staging before public rollout.
8. **Verify operational safeguards.** Configure `TRUST_PROXY` for the actual trusted proxy addresses or hop count; forwarding headers are not trusted by default. Confirm distinct clients receive distinct rate-limit identities without accepting spoofed headers. Confirm least-privilege database/hosting access, backups and retention, shared rate limiting across workers, monitoring/alert ownership, SMTP delivery, and an incident-response process. Confirm `privacy@uficonnect.org` is monitored and that the privacy policy's retention and response commitments match actual operations. These hosted settings cannot be proven by local source review.
9. **Apply release gates.** Render's built-in auto-deploy is disabled in the blueprint. The GitHub deployment workflow triggers configured `RENDER_HOOK_API`, `RENDER_HOOK_WEB`, `RENDER_HOOK_OFFICE`, and `RENDER_HOOK_PIPELINE` secrets only after verification succeeds. It pins the verified commit and checks that it remains the current `main` commit before each trigger. Pages also verifies freshness immediately before publishing. This ownership is explicit because [Render's exact-commit hook parameter disables its automatic deploys](https://render.com/docs/deploys#deploying-a-specific-commit). Confirm all intended hooks exist in GitHub secret settings; absent hooks do not deploy their services. A successful trigger does not prove that Render finished its build or rollout. Mobile verification includes security tests, dependency auditing, Expo validation, three-platform production exports, and exported-app browser checks before an EAS release build can be queued. Apply these settings to the live services and confirm final health after rollout. Existing Render services need new `sync: false` values entered manually; a blueprint update does not populate them.

## Verification

The existing Office and hosting administrator controls can initiate manual deployments. Keep these capabilities restricted and require operators to verify the intended commit and release checks before using them; the automatic-workflow gates do not certify an administrator-triggered release. Local container examples are documented in [CONTAINERS.md](CONTAINERS.md); they are loopback-only development/validation setups, not public HTTPS deployment configurations.

Run from the repository root after installing dependencies:

```sh
node scripts/check-js.cjs
npm test --prefix backend
node --test scripts/office-security.test.mjs scripts/web-security.test.mjs
npm run test:security --prefix mobile
node scripts/check-deployment-security.mjs
node scripts/sync-security-headers.mjs --check
npm run build --prefix web
npm run build --prefix office
node scripts/sync-security-headers.mjs --check --built
node scripts/audit-security.mjs
node scripts/audit-csp.mjs
node scripts/audit-office-pipeline.mjs
npm audit --prefix backend --audit-level=high
npm audit --prefix web --audit-level=high
npm audit --prefix office --audit-level=high
npm audit --prefix mobile --audit-level=high
```

The verification workflow also runs Expo doctor, production exports for Android, iOS and web, and the exported-app browser audit. See [native validation](../mobile/DEPENDENCY_SECURITY.md) for the exact commands and supported runtime.

- Backend: 125 tests passed, including unchanged-password rejection, common-password screening, concurrent updates, database write failures, old/new credential verification, reset-token isolation, revocation, profile privacy, encrypted credentials, TLS, provider-account deletion, and the isolated analytics document's security headers.
- Web and Office security units: 9 tests passed. Web browser security checks: 388 passed at desktop and phone widths, including reveal/hide, keyboard access, caret preservation, clipboard export, immediate lifecycle concealment, common/unchanged-password rejection and successful updates. The built web app loaded under both HTTP and meta CSP while injected scripts were blocked.
- Web and Office production builds passed; the generated CSP matches the built inline scripts. Deployment YAML validation passed.
- All 12 existing web browser audit suites passed during the initial security baseline, including navigation, responsive settings/sidebar, feeds, travel, notifications, source favorites, post context and content history. The Office pipeline browser audit passed at four viewport widths after the Show/Hide follow-up, including credential concealment and responsive dialog checks.
- Backend, web, Office and native dependency audits reported zero known vulnerabilities in the resolved trees on September 15, 2026.
- Native: 26 security/compatibility and analytics unit tests passed, including a component regression for secure native inputs with a non-selectable preview. All 21 Expo doctor checks passed during the SDK upgrade. Production web JavaScript and Android/iOS Hermes bytecode exports passed after the analytics follow-up. The exported web app passed 106 security checks at phone and desktop widths. These exports are not signed installable binaries.
- Optional Google Analytics: 9 shared-controller tests, 64 main-web browser checks and 40 Expo-web analytics browser checks passed. The main document still blocks Google scripts under both HTTP and meta CSP. Separate probes with the real Google SDK verified safe page-view payloads, parent-origin isolation and partitioned-cookie cleanup; collection was intercepted locally, so live GA receipt is not claimed. See [activation and native prerequisites](GOOGLE-ANALYTICS.md).

Native unit/configuration checks do not replace testing installed iOS/Android builds, keyboard behavior, device storage, backup restoration, and OS screenshots. Dependency audit results cover known advisories in the resolved dependency graph, not application logic or unknown vulnerabilities. Production cloud settings, migration of real data, and credential rotation have not been performed or verified by this local review.
