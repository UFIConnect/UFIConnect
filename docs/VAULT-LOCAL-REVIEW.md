Your Vault is a browser vault beta available to signed-in UFIconnect users at `/vault`. Password storage is encrypted locally and separated by the signed-in account in that browser. Publishing the page does not upload passwords, provide cloud synchronization, or connect physical UFI hardware. The public VPN panel helps users manage an existing Windows or iOS VPN through their own device; it does not claim that the browser can establish or verify a VPN tunnel.

For a separate local review, start this checkout with `node scripts/start-vault-review.mjs`, then use the printed URL, normally `http://localhost:4187/vault`. The launcher binds to the local computer and uses a synthetic account with separate browser storage from the public website. Use test entries while reviewing it. The `LOCAL PREVIEW` badge and Windows adapter requests require both `VITE_VAULT_LOCAL_PREVIEW=true` and a loopback hostname. Public builds show `BROWSER VAULT · BETA` and never poll or probe the local VPN service.

The local launcher disables optional analytics and aggregate page tracking, blocks cross-origin VPN requests, and prevents embedding the preview in another page. Vault data is never posted to the local helper; only VPN profile IDs are sent for explicit connection actions. Keep the preview on the local computer rather than exposing its port to a network.

Passwords are encrypted in the browser before being saved to this origin's `localStorage`, under an account-specific storage key. The application waits for an authenticated account before mounting the Vault and locks on sign-out; switching accounts uses a separate Vault. This separation is not a substitute for encryption on a shared or compromised computer. There is no UFIconnect account sync, cloud backup, or server-held recovery key. Keep using the same account, browser profile, hostname, and port: another browser profile or origin has different storage. Clearing site data, removing the browser profile, or losing the computer can remove the only stored copy. Private browsing is unsuitable for durable storage. Legacy unscoped local-preview storage is left untouched; export an encrypted backup from the earlier preview and restore it explicitly to move those entries. [MDN: browser localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage).

The implementation uses a random 256-bit data key, AES-GCM authenticated encryption with fresh 96-bit IVs, and PBKDF2-HMAC-SHA-256 with a random 128-bit salt and 600,000 iterations to derive the passphrase wrapping key. Passphrases and unwrapped data keys are not written to browser storage. Names, websites, usernames, passwords, and notes are inside the encrypted content. Browser memory necessarily holds decrypted entries while the Vault is unlocked; encryption at rest does not protect an already compromised browser or computer. The UI locks after a minute of inactivity or when the page is hidden. [W3C Web Cryptography](https://www.w3.org/TR/webcrypto/), [AES-GCM parameters](https://developer.mozilla.org/en-US/docs/Web/API/AesGcmParams), [PBKDF2 parameters](https://developer.mozilla.org/en-US/docs/Web/API/Pbkdf2Params).

Recovery depends on an encrypted backup and the passphrase that was used for that backup:

1. Choose a strong, unique passphrase and keep a recovery copy separately from the computer and backup file. There is no email reset or administrator override that can decrypt a forgotten passphrase.
2. Download an encrypted backup after adding or changing entries. Keep more than one known-good version outside browser storage.
3. Confirm that a backup and its passphrase can unlock in a separate browser profile before relying on them. A successful file download alone does not prove recovery works.
4. Before replacing an existing Vault, export its current encrypted backup. Restore the intended encrypted file and unlock with that file's passphrase. A restored backup contains the entries present when it was exported.

Device unlock is optional and does not replace recovery backups or the passphrase. It uses the browser's WebAuthn PRF extension to derive a key that can unwrap the Vault's data key. The operating system and browser must support both platform passkeys and PRF, and must complete user verification. A generic successful biometric prompt without PRF key material cannot unlock this Vault. Face ID is available only where the operating system, browser, and authenticator support that workflow; the application cannot add or force Face ID on an unsupported device. Verification may instead use another biometric or the device's PIN. If support is missing or a passkey is lost, use the passphrase. The platform's own passkey backup or sync behavior is separate from this application's lack of Vault sync. [W3C WebAuthn PRF](https://w3c.github.io/webauthn/#prf-extension), [W3C user verification](https://w3c.github.io/webauthn/#user-verification), [MDN PRF support and results](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API/WebAuthn_extensions#prf).

Password import accepts common CSV login columns and supported JSON login exports. Files are processed in the browser, with a 2 MB import limit and a maximum of 1,000 entries in the Vault. Import appends login entries; it does not migrate every feature of another password manager, attachments, or other item types. Imported export files may contain plaintext passwords even though the saved Vault is encrypted. Keep those original files controlled and remove copies you no longer need after checking the import and encrypted backup. Copying a password also places plaintext on the operating-system clipboard; locking the Vault does not erase clipboard history.

The public VPN panel offers Windows and iPhone & iPad instructions, initially selecting iOS on iPhones and iPads, including iPadOS desktop user agents. Its status is `Managed on your device`, with `Status unavailable in browser` explained alongside the instructions. It never infers that a VPN is disconnected simply because browser access is unavailable, and it does not log clicks as connection events. Users connect or disconnect in their existing provider app or operating-system VPN profile. The public site does not expose a pretend Connect button, request VPN credentials, create a subscription, or silently install profiles.

On iPhone and iPad, use the installed VPN provider app or open **Settings → General → VPN & Device Management → VPN** and select the existing profile. Check connection status in the app or Settings before returning to the Vault. The web page cannot read the profile, invoke iOS Network Extension APIs, toggle the tunnel, or force-open Settings with an unsupported URL scheme. The Apple VPN guidance link is a normal HTTPS link, not an app launch. A native app with the appropriate platform integration would be needed for direct control. Apple notes that some essential system traffic may operate outside an active VPN. [Apple VPNs & Privacy](https://www.apple.com/legal/privacy/data/en/vpns/).

On Windows, the public panel links to `ms-settings:network-vpn` only when Windows is detected and otherwise displays manual settings instructions. In-page Connect and Disconnect require the separate local launcher, not the public website. Configure a profile in Windows Settings first. The local adapter reads current-user and all-user profiles with `Get-VpnConnection`, then permits controls only for profiles explicitly configured as IKEv2 or SSTP. Automatic, PPTP, L2TP, unsupported protocols, and unknown states remain unavailable in this panel. Windows must already hold any credentials the profile requires. [Microsoft Get-VpnConnection](https://learn.microsoft.com/en-us/powershell/module/vpnclient/get-vpnconnection), [Microsoft VPN protocol guidance](https://learn.microsoft.com/en-us/windows-server/remote/remote-access/configure-vpn-protocols), [Microsoft connection types](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/vpn/vpn-connection-type).

Connect and Disconnect run only after the corresponding user action. The server checks the local Host and Origin plus a CSRF token before invoking a currently configured profile. The adapter passes separate, whitelisted arguments to `rasdial.exe` without a shell, never sends a password, and reads Windows status again afterward. A successful process exit does not by itself mean that a tunnel is connected. If a profile has split tunneling enabled, some traffic bypasses that VPN. Connection status does not prove protection from every IP or DNS leak, provide a kill switch, or guarantee anonymity. [Microsoft rasdial](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/ff859533(v=ws.11)).

Local companion connection activity contains at most 50 in-memory timestamps and requested Connect/Disconnect actions. These entries describe requests, including requests that may fail; they are not proof of successful connections. They contain no browsing history, destination addresses, traffic contents, profile names, or VPN credentials. Restarting the local launcher clears this activity. The public site and iOS panel state that activity is unavailable in the browser; neither fabricates connection events nor receives the device's VPN history. Windows, iOS, and the chosen VPN provider can maintain their own records outside this application.

The physical Vault device is still pending. No hardware storage, hardware pairing, device attestation, or hardware-backed recovery has been validated. The local UI and browser passkey integration must not be presented as a completed physical-device integration.

This implementation has not received an independent security audit. Functional tests and code review can identify defects, but they do not certify the encryption design, dependency chain, operating system, browser, VPN provider, or pending hardware. The localhost controls are intended for a trusted local computer; they are not a security boundary against another process already running with access to that computer.
